## 2. Предлагаемая модель

Проект содержит корневые задачи, у корневой задачи могут быть подзадачи.
Самостоятельная корневая задача также может иметь подзадачи без проекта.
Третий уровень запрещён. Подзадачи остаются строками `tasks`, а не отдельной
таблицей и не элементами JSON-разбивки трудозатрат.

Добавить к Project:

- `description`, `started_at`;
- `auto_due_at`, `manual_due_at`, `planned_due_at`;
- `revision` для проверки актуальности черновиков.

Добавить к Task:

- `parent_task_id` — nullable FK на tasks, индекс, запрет самоссылки,
  удаление родителя с детьми через FK RESTRICT;
- `complexity`, `task_type` — nullable классификация с проверкой значений;
- `scheduled_start_at`, `scheduled_end_at` — nullable явные интервалы работы;
- `revision`.

Начальный набор сложности: simple/standard/complex. Типы задач — явная
настраиваемая классификация, например list/document/research/analysis/
implementation/review/other; старые строки остаются без назначенного типа.

Для фактического времени — `task_time_entries`: task ID, минуты, дата,
источник/комментарий, UUID операции. Записи только по явному вводу владельца.
Плановая оценка уже хранится в `estimate_minutes`. История оценок —
`task_estimate_revisions`: оценка, этапы, категория, причина и время изменения.
Отклонение вычисляется относительно явно выбранной версии оценки, например
оценки на начало работы, а не скрыто меняющейся последней оценки.

Прогресс, суммарное время и риски отдаёт сервис сводок. Для первой версии
не создавать отдельный редактируемый список рисков в Project: фактические
риски вычислять по данным, предположения модели показывать отдельно с датой.

## 3. Правила целостности и совместимости

- Все существующие Task после миграции имеют `parent_task_id = NULL`.
  Существующие даты, статусы, оценки и evidence не переписываются.
- Не извлекать родителя автоматически из EventLog: это отдельная явно
  подтверждаемая операция после проверки возможных кандидатов.
- Родитель и ребёнок имеют одинаковый project ID, включая оба NULL.
  Самоссылки, третий уровень и дети закрытого родителя запрещены.
- Межстрочные ограничения нельзя обеспечить одним SQL CHECK: нужны
  PostgreSQL constraint triggers и согласованный порядок блокировок.
  Проверить конкурентное создание детей/смену родителя отдельными тестами.
- При отмене родителя показать незавершённых детей и зависимые задачи.
  Никакого скрытого каскада: массовая отмена требует отдельного UUID-черновика.
  В первой версии использовать отмену вместо физического удаления.
- Не закрывать родителя или проект с незавершёнными действующими детьми.
  100% прогресса не заменяет ручное принятие результата.
- Не превращать фразу «задача готова» в обход evidence и `/verify`.
- В сводной трудоёмкости считать листья: если у родителя есть действующие
  дети, его итоговая оценка — сумма оценок детей, без добавления прежней
  общей оценки родителя. Старую оценку сохранять для сравнения.
  Непокрытую работу оформлять отдельной подзадачей, а не скрытым остатком.
- Если часть оценок неизвестна, показывать «известно X минут + неоценённые
  работы», не выдавать неполную сумму за итог. Аналогично для actual time.
- Прогресс считать по завершённым действующим листьям; отменённые исключать.
  Для равномерного счётчика явно писать «N из M», без выдуманных процентов
  фактической готовности. Взвешивание допустимо только при полных оценках.

## 4. Сервисный слой и Telegram

Сохранить `db.py`, `ai.py`, `workflow.py`, существующие команды и стек.
Добавить небольшие модули:

- `services/tasks.py`, `services/projects.py`, `services/hierarchy.py` —
  единые операции, переходы и ограничения;
- `services/planning.py` — сроки, агрегаты, проверка зависимостей/интервалов;
- `services/estimates.py` — сумма этапов, история и калибровка;
- `intents.py`, `schemas.py`, `resolution.py` — разбор запроса, строгая
  структура ответа модели и поиск конкретной сущности;
- `settings.py` — проверяемая конфигурация порогов и правил дат.

Обработчики `main.py` переводить на сервисы по одной группе операций.
Полное переписывание файла не требуется. Важно провести через один сервис
и `/move`, и кнопку переноса, и групповой перенос, и естественный язык:
иначе пересчёт срока проекта будет зависеть от выбранного интерфейса.

Общий путь: запрос → типизированное намерение → поиск сущности → валидация
и прогноз последствий → UUID-черновик → показ пользователю → повторная
проверка версий и прав → одна транзакция → EventLog → ответ.

Модель не исполняет SQL и не выбирает произвольные поля ORM для обновления.
Для каждой операции — белый список полей и допустимых переходов.
Старые действующие UUID-кнопки сохраняют свой протокол либо безопасно
отклоняются при несовместимой версии; никогда не меняют смысл операции.

Поиск: явный ID, затем однозначное нормализованное имя в заданном проекте.
При нескольких кандидатах показать ID, название, проект и статус.
Сходство используется для вариантов, не для молчаливого выбора.
Ссылка «эта задача» разрешается через сохранённый контекст владельца;
если актуальной однозначной ссылки нет — уточнение.

## 5. Классификация и оценки

Модель предлагает структуру и независимо принимаемые результаты. Python
проверяет её и применяет настраиваемые критерии. Один результат с этапами
оценки остаётся одной задачей. Несколько отдельно принимаемых частей одного
результата могут стать подзадачами. Несколько самостоятельных результатов
в разных направлениях — кандидат в проект.

Начальные настройки для обсуждения:

- кандидат в проект: минимум 3 самостоятельных результата и 2 направления;
- дополнительные сигналы масштаба: не менее 2 рабочих дней трудозатрат или
  горизонта 10 рабочих дней; каждый из них отдельно проект не создаёт;
- предложение подзадач: минимум 2 части, каждая имеет отдельный критерий
  приёмки, а не только название этапа оценки;
- неоднозначность или противоречащие друг другу сигналы → уточнение.

Обоснование: отделить несколько результатов и направлений от одной сложной
работы; числовые пороги — начальные эвристики, не объективный стандарт.
Вынести их в настройки, версионировать и проверить на примерах ТЗ. Отдельно
ограничить размер плана и выводить полный черновик с пагинацией — не
обрезать содержимое перед кнопкой подтверждения.

Для короткого списка из пяти пунктов стартовая подсказка — один этап и
порядок 5–20 минут при наличии исходных знаний. Это ориентир, а не жёсткий
потолок: при необходимости исследования модель должна объяснить разницу.
Сумма этапов всегда вычисляется в Python. Двойной учёт этапов запрещён.
Расхождения/необоснованно большая оценка вызывают уточнение, а не скрытую
подмену числа. Калибровку показывать с числом наблюдений; до накопления
например 10 сопоставимых завершённых задач не применять поправку молча.

## 6. Статусы, сроки и риски

Проект: draft → planned/active/cancelled; planned → active/cancelled;
active → paused/completed/cancelled; paused → active/cancelled.
completed/cancelled — терминальные без специального сценария восстановления.
Совместимость `/approve`: сохранить явный переход draft/planned → active,
но запретить возобновление закрытого проекта этой командой.
Пауза проекта не переписывает статусы детей; планировщик учитывает паузу.

Новый проект с задачами до подтверждения хранится только в UUID-черновике.
После подтверждения проект в `planned` и его задачи сохраняются одной
транзакцией. Подготовка задач разрешена в planned/active; начало исполнения
требует active. Это осознанное расширение текущего ограничения «задачи
разрешены только в active», необходимое для предварительного планирования.

`auto_due_at` — максимум сроков всех незакрытых задач проекта, включая детей.
`manual_due_at` — явное обязательство владельца. `planned_due_at` равен
ручному сроку, если он задан, иначе автоматическому. Если auto позже manual,
показывается риск нарушения ручного срока; manual не изменяется.
Нет действующих задач со сроками → auto NULL. При наличии задач без сроков
указать неполноту расчёта. Дата завершённого проекта — отдельный исторический
факт в журнале, а не выдуманный срок оставшихся работ.

Пересчёт выполняется в той же транзакции после создания, переноса,
привязки к проекту, отмены, завершения и изменения подзадач. Перед записью
блокировать затронутые проекты/задачи в стабильном порядке; revision
защищает от применения черновика после любых промежуточных изменений.

Относительные даты разбирать от явного текущего московского времени.
Если меняют только день — сохранять прежнее московское время, при его
отсутствии использовать настраиваемые 18:00. Необоснованный дедлайн — NULL.
Прогноз последствий включает прежний/новый срок проекта, просрочку,
конфликты направленных зависимостей и нарушение ручного срока.
Пересечение работ объявлять фактом только при явных интервалах расписания;
совпадение дедлайнов не доказывает перегрузку.

Сохраняем запрет циклов TaskDependency; при добавлении иерархии запрещаем
зависимости между предком и потомком и проверяем циклы на графе исполняемых
листовых работ, учитывая агрегирующие родительские узлы. Обычная
декомпозиция сама по себе не создаёт зависимость «родитель → ребёнок».
Изменения связанных задач требуют явного группового черновика.

## 7. Новые миграции (предлагаемые имена)

| Ревизия | Изменения | Проверка до подключения приложения |
| --- | --- | --- |
| 0003_task_hierarchy | parent_task_id, FK RESTRICT, индекс, ограничения двух уровней и общего проекта | Самоссылки, отсутствующий/закрытый родитель, конкурентные записи; все старые parent NULL |
| 0004_project_planning | Описание/даты Project, revision для Task/Project, поля расписания Task | Сохранность ID, статусов и старых сроков; все новые даты изначально NULL |
| 0005_effort_history | Категории, журнал плановых оценок и фактического времени | Неотрицательные значения, повторный UUID, отсутствие выдуманных actual time |

Существующие 0001/0002 не редактировать. Даты проектов и отношения старых
«следующих шагов» не заполнять догадками. Новый проектный статусный автомат
не требует переименования прежних значений. Перед добавлением ограничений
проверить реальные значения: несовместимости отчётно останавливают миграцию,
не исправляются массовым UPDATE без отдельного решения.

Проверка каждой ревизии: новая пустая PostgreSQL 16; копия схемы 0002 с
контрольными проектами, задачами и evidence; обновление по шагам и до head;
сохранение данных и FK; повторный запуск; откат транзакции при несовместимости.
Проверку metadata адаптировать так, чтобы она не мешала легитимным
промежуточным ревизиям и созданию новых миграций. На рабочей БД не проверять.

## 8. Очерёдность и критерии завершения

1. Этот аудит и рассмотрение архитектуры/правил совместимости.
2. Модели и 0003; тесты иерархии на изолированной PostgreSQL.
3. 0004/0005 и общие сервисы; существующие команды используют их без потери
   функций; миграционные тесты и прежние 21 тест адаптированы и проходят.
4. Структурированная классификация и оценки; фикстуры трёх примеров ТЗ,
   уточнение неоднозначности, отсутствие искусственных подзадач.
5. Управление существующими задачами по ID/имени, включая редактирование
   полей, фактическое время, декомпозицию и отмену; UUID и проверки версий.
6. Статусы проектов, сроки и прогноз рисков; тесты ручного срока и паузы.
7. Полные Telegram-сценарии с mock API, конкурентные подтверждения,
   сохранность после переподключения и тестовые rollback-сценарии.
8. Docker Compose: миграция, запуск без root, heartbeat, резервирование,
   восстановление; затем отдельные ручные проверки Telegram.

После каждого этапа — перечень файлов, реально выполненные тесты и
обнаруженные ограничения. После изменения данных транзакция содержит и
пересчёт сводок, и EventLog, и погашение UUID. Никакого частичного применения.
Публикация среды и изменения старой рабочей базы в этот план не входят.

Ручные сценарии: простой список; сложный документ; проект стратегии;
неоднозначное имя; «завтра» с сохранением времени; добавление трёх подзадач;
отмена и повторное нажатие; пауза/возобновление проекта; перенос предшественника
за срок зависимой задачи; ручной срок проекта; сдача/проверка детей и родителя.
Перед живыми проверками отдельно подтвердить целевую тестовую БД и доставку
через настроенный прокси, не отправляя сообщения в процессе аудита.
