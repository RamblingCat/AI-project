# Развитие проектов, задач и подзадач

## Реализованные функции

- Двухуровневая иерархия: проект → задачи → подзадачи; самостоятельные задачи
  также могут иметь детей. Внешний ключ, CHECK и deferred PostgreSQL trigger
  запрещают самоссылки, третий уровень, несовпадающие проекты и закрытие
  родителя с незавершёнными детьми. Удаление родителя с детьми запрещено FK.
- Создание обычной задачи, задачи с детьми или проекта с задачами через
  единый подтверждаемый план. Новый проект сохраняется в `planned`, работа
  начинается после перевода в `active`. Существующие ID и команды сохранены.
- Классификация учитывает отдельно принимаемые результаты, направления,
  трудоёмкость и горизонт. Разбивка оценки не превращается автоматически
  в подзадачи. Неоднозначный масштаб или имя вызывают уточнение.
- Редактирование названия, описания, критериев, приоритета, дедлайна,
  оценки, категории, расписания и допустимых статусов обычным языком.
  Создание и отмена подзадач используют те же правила. Приёмка остаётся
  через evidence и `/verify`; фраза «готово» не закрывает задачу автоматически.
- Поиск по явному ID или однозначному названию. При нескольких совпадениях
  показываются варианты с ID, статусом и проектом. «Эта задача» разрешается
  только через сохранённый однозначный контекст владельца.
- Статусы проектов draft/planned/active/paused/completed/cancelled,
  подтверждаемые переходы и запрет повторного открытия через `/approve`.
  Проект не завершается при незакрытых задачах. Пауза проекта исключает
  его работы из инициативных отчётов и напоминаний, не меняя статусы детей.
- Сумма этапов считается программно. Родитель с действующими детьми
  получает сводную оценку по детям; прежняя общая оценка не прибавляется.
  Неоценённые работы и незаполненное фактическое время показываются явно.
- История оценок, снимок оценки на начало работы и фактическое время,
  вводимое владельцем. Пример: «Запиши 25 минут по задаче №3». Запись
  подтверждается UUID и не дублируется повторным нажатием.
  Калибровка по сопоставимым завершённым листовым задачам показывает число
  наблюдений и коэффициент факт/план. Она не меняет оценки автоматически.
  Итоговое отклонение факт−план вычисляется из сохранённой истории и
  показывается только после завершения работ с полными записями времени;
  до этого оно отмечается как неизвестное.
- Автоматический срок проекта — максимум дат незакрытых задач и подзадач.
  Изменение Task пересчитывает его PostgreSQL-триггером в той же транзакции,
  включая старые команды. Ручной срок хранится отдельно и имеет приоритет
  в итоговом плановом сроке; превышение вызывает предупреждение.
- Проверка зависимостей, просрочки, сроков родителя и ручного срока проекта.
  Пересечение объявляется только для заданных интервалов расписания,
  а не по совпавшим дедлайнам. Проверка циклов учитывает агрегирующие
  родительские узлы. Связанные задачи автоматически не переносятся.
- `/hierarchy` показывает дерево, прогресс N/M, известную оценку/факт и
  количество работ без оценки/записей времени. `/projects` показывает
  прогресс, итоговый и ручной срок, число работ без дедлайна.

## Подтверждения и транзакции

Предпросмотр сначала проверяет операцию в savepoint, затем полностью
откатывает пробные изменения. До подтверждения остаётся только UUID-черновик
и контекст выбора. PostgreSQL sequences могут иметь пропуски после таких
откатов — ID не обозначают количество записей.

Каждый черновик имеет UUID и TTL 24 часа. Старое предложение той же
операции заменяется новым. Перед применением проверяются владелец,
версии записей и контекст проекта/зависимостей. Изменение значения и
последующий возврат к старому значению не делает старую кнопку действительной.
Связанные изменения могут потребовать нового черновика даже при неизменном
целевом поле: это защищает актуальность показанных последствий.

Относительные даты разрешаются при подготовке, фиксируются абсолютной
московской датой и повторно проверяются на актуальность при применении.
Запрос «на завтра» сохраняет прежнее московское время дедлайна; при его
отсутствии используется 18:00, настраиваемое через окружение.
Полный черновик разбивается на сообщения, кнопки отправляются после всех
его частей. Запись дерева, журнал и погашение UUID атомарны.

Для одного владельца операции сериализуются PostgreSQL advisory lock с
единым порядком блокировок. Это сознательный выбор корректности для данного
бота; для многопользовательской высоконагруженной версии потребуется
разделить блокировки по владельцам/проектам.

## Изменения БД

| Ревизия | Изменения |
| --- | --- |
| `0003_task_hierarchy` | parent_task_id, FK RESTRICT, индекс, CHECK и deferred trigger иерархии |
| `0004_project_planning` | description/started_at/auto_due_at/manual_due_at/planned_due_at проекта, revision проекта и задачи, интервалы расписания, триггеры версий и пересчёта |
| `0005_effort_history` | complexity/task_type, task_time_entries, task_estimate_revisions, ограничения и индексы |

Ревизии 0001/0002 не переписаны. Старые задачи остаются корневыми;
исторические «следующие шаги» из EventLog автоматически не перепривязываются.
Существующие статусы, даты, оценки и evidence не заменяются догадками.
Новые поля фактического времени не заполняются автоматически. Срок старого
проекта первоначально неизвестен и рассчитывается после последующих
изменений его задач; это исключает массовое изменение исторических данных.

## Основные изменённые файлы

- `app/db.py`, `app/workflow.py`, `app/dependencies.py` — модели,
  версии подтверждений, иерархические зависимости.
- `app/main.py`, `app/ai.py` — подключение сервисов к существующим
  обработчикам, новым запросам и сводкам; основной файл не переписан целиком.
- `app/settings.py`, `app/schemas.py`, `app/intents.py`, `app/resolution.py`,
  `app/natural.py` — настройки, валидация, модель намерений, поиск и превью.
- `app/services/tasks.py`, `projects.py`, `planning.py`, `proposals.py` —
  операции и единые правила.
- `migrations/versions/0003_*.py`–`0005_*.py` — новые миграции.
- `tests/test_workflow.py`, `tests/test_v2.py` — регрессия, реальные
  обновления схемы 0002 и новые сценарии.
- `compose.v2.yml`, `.env.v2.example`, `.env.example`, `.gitignore`,
  `README.md`, `ARCHITECTURE_V2_PLAN.md`, этот документ — запуск и описание.

Новых библиотек не потребовалось, зафиксированный requirements.txt сохранён.

## Настройки и обоснование стартовых значений

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| PM_PROJECT_RESULTS | 3 | Минимум самостоятельных результатов для кандидата в проект |
| PM_PROJECT_WORKSTREAMS | 2 | Независимые направления; сложность одной работы не равна проекту |
| PM_PROJECT_EFFORT_MINUTES | 960 | Два 8-часовых рабочих дня: повод уточнить крупную недекомпозированную работу |
| PM_PROJECT_HORIZON_DAYS | 10 | Сигнал длинного календарного горизонта в объяснении классификации |
| PM_MAX_PLAN_TASKS | 20 | Ограничение общего числа работ одного подтверждения |
| PM_SIMPLE_REVIEW_MINUTES | 30 | Для простой задачи более высокая оценка требует уточнения |
| PM_DEFAULT_DEADLINE_HOUR | 18 | Московское время при отсутствии прежнего/явного времени |
| PM_CALIBRATION_SAMPLES | 10 | Минимальное число сопоставимых наблюдений для коэффициента |

Это изменяемые эвристики, а не нормативы производительности. Большая
оценка, срок через три месяца или длинный текст отдельно проект не создают.
Если наблюдений меньше минимума, статистика не выдаётся за точную модель.

  прежние 21 сценарий и 20 новых. Проверены иерархия, оценки, проекты,

  конкурентные черновики/создание детей, относительные даты, фактическое
  время и калибровка, конфликты и отсутствие ложного вывода о пересечении.

  0005: сохранение контрольных записей, повторный запуск, транзакционный
  отказ при неизвестном несовместимом поле.
- Docker-образ собран. Контейнер UID 10001 применил 0001–0005 в отдельной
  временной БД, сохранил родителя и двух детей, подтвердил сумму оценок,

## Отдельный тестовый запуск Docker Compose

Требуется Docker Compose >= 2.24.4 (`!override` для отдельного env_file).
В существующем каталоге `telegram_ai_pm` создайте **новый** `.env.v2` из
`.env.v2.example`, не перезаписывая имеющиеся `.env` или `.env.v2`.
Введите секреты безопасно, задайте пароль PostgreSQL и соответствующий
URL-кодированный пароль в DATABASE_URL. Имя БД — `telegram_ai_pm_v2`.

```sh
mkdir -p secrets
docker compose -p telegram_ai_pm_v2 --env-file .env.v2 -f docker-compose.yml -f compose.v2.yml build bot
docker compose -p telegram_ai_pm_v2 --env-file .env.v2 -f docker-compose.yml -f compose.v2.yml up -d db
docker compose -p telegram_ai_pm_v2 --env-file .env.v2 -f docker-compose.yml -f compose.v2.yml run --rm --no-deps --entrypoint python bot -m app.migrate
docker compose -p telegram_ai_pm_v2 --env-file .env.v2 -f docker-compose.yml -f compose.v2.yml up -d bot backup
docker compose -p telegram_ai_pm_v2 --env-file .env.v2 -f docker-compose.yml -f compose.v2.yml ps
```

Этот project name создаёт отдельные сеть и тома; нельзя указывать рабочий
DATABASE_URL или использовать прежние внешние тома. Дождитесь готовности db
перед отдельной командой миграции. Обычный старт бота также применяет миграции.
Не запускайте два polling-процесса с одним BOT_TOKEN: для теста нужен отдельный
бот либо остановленная другая копия. Прокси/TLS интеграция реальных API
проверяется отдельно; сертификат сборки передаётся BuildKit secret, как в README.

Для существующей тестовой БД сначала остановите её бота, создайте и проверьте
дамп по README, затем применяйте миграции свежим образом. Destructive downgrade
не реализован; откат выполняется восстановлением проверенной копии.

## Ручные проверки Telegram и ограничения

1. Короткий список из пяти вариантов → одна задача и умеренная оценка;
   до нажатия кнопки в `/hierarchy` ничего нового нет.
2. Инструкция с отдельно принимаемыми частями → задача с детьми; крупная
   многопрофильная стратегия → предложение проекта и задач.
3. Два похожих названия → варианты с ID, без случайного изменения.
4. «Повысь приоритет задачи …», «Переименуй …», «Измени критерии …» →
   прежнее/новое значение, подтверждение, EventLog.
5. «На завтра» → конкретная московская дата с прежним временем.
6. «Предложи структуру» → только анализ. «Добавь три подзадачи» → черновик;
   отмена, повторное нажатие и третья вложенность не меняют данные.
7. Приостановка/возобновление проекта; запрет его завершения с активными
   задачами и повторного открытия завершённого проекта через `/approve`.
8. Перенос предшественника за срок зависимой задачи → предупреждение;
   ручной срок проекта сохраняется. Равные дедлайны не объявляются
   невозможностью одновременного выполнения.
9. Запись фактического времени, сдача и приёмка детей/родителя;
   проверка сводных оценок без двойного учёта.

Живое качество распознавания конкретной моделью и реальная доставка Telegram
не подтверждены автоматическими mock-тестами; эти ручные проверки не выполнены.
Распределение уже записанного времени родителя при последующей декомпозиции
требует отдельного решения: сейчас такая декомпозиция отклоняется, чтобы
не скрывать и не дублировать время. Физическое удаление заменено отменой.
Старые next_step-черновики могут создавать детей с неизвестной оценкой;
сводка честно показывает их как неоценённые.

Нагрузочное календарное планирование, автоматическое распределение ресурсов,
перенос связанных задач без согласования, исправление исторических связей
и автоматическая поправка оценок не выполняются.
